## Why this is blocked in the current session

This cloud sandbox's network egress policy blocks the host GitHub Actions
artifact downloads redirect to. Confirmed directly, this session:

1. Called the GitHub artifact-download API for artifact ID `8118169559`
   (`phase2a-firmware-artifacts`) — it returned a valid, time-limited
   download URL pointing at
   `productionresultssa12.blob.core.windows.net` (GitHub Actions artifacts
   are always served from Azure Blob Storage via a redirect, not from
   `api.github.com` or `objects.githubusercontent.com` directly — this is
   inherent to how the GitHub Actions artifact API works, not a
   misconfiguration).
2. Attempted to fetch that URL directly (`curl`) — got `CONNECT tunnel
   failed, response 403`.
3. Confirmed via this session's own proxy status endpoint
   (`$HTTPS_PROXY/__agentproxy/status`) that the most recent relay failure
   is exactly this: `"kind":"connect_rejected"`,
   `"host":"productionresultssa12.blob.core.windows.net:443"`,
   `"detail":"gateway answered 403 to CONNECT (policy denial or upstream
   failure)"`.
4. Also confirmed direct calls to `api.github.com` itself return `403` from
   this sandbox's proxy (the earlier successful GitHub API calls in this
   project went through a separate MCP connector, not this session's own
   outbound network path) — so there is no alternate GitHub-hosted route
   available either.

This is the same class of environment limitation documented throughout this
project (the Flipper toolchain host block in `BUILD_LOG.md`/`KNOWN_ISSUES.md`,
and this same sandbox's inability to execute `fbt.cmd` at all): **a real,
external network policy denial, not a defect in the tooling, the firmware,
or the apps.** Per this project's standing rule, this is reported honestly
rather than routed around or faked.

## How to actually generate this manifest

Two ways, either of which produces real values to replace the rest of this
document:

**Option A — download and hash locally** (on any machine with network
access to GitHub, which this cloud sandbox does not have for this specific
purpose):
1. Open https://github.com/XXBlackMartinXX/Custom-Flipper/actions/runs/28814008347
2. Download both artifacts (`phase2a-firmware-artifacts`,
   `phase2a-validation-reports`) from the run's Artifacts section, and
   extract each zip.
3. Run, for each extracted directory:
   ```powershell
   .\tools\phase2a_artifact_manifest.ps1 -ArtifactDir "<extracted-dir>" -OutFile .\docs\PHASE2A_ARTIFACT_HASHES.md
   ```
   (run it twice with `-OutFile` pointed at two different files, or combine
   both directories under one parent and scan once, if you prefer a single
   report covering both artifacts).
4. Replace this document's content with the generated Markdown table, or
   append it below this explanation.

**Option B — have the CI workflow hash the files itself**, immediately
after building them and before upload, so the hashes appear in the
uploaded `phase2a-validation-reports` artifact without anyone needing to
download the (larger) firmware artifact just to hash it. This would require
a small addition to `.github/workflows/phase2a-windows-validation.yml` (a
`Get-FileHash` step) and one more CI run — not implemented in this pass, out
of scope for this specific change without separate confirmation since it
touches the workflow file.
